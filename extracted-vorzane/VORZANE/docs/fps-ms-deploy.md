# FPS.ms deployment (backend foundation)

Build from repository root using `docker build -f Dockerfile.backend -t vorzane-backend .`. The image runs Prisma migrations and then the Node service. If deploying from a source checkout instead: working directory `backend`; `npm install`, `npx prisma generate`, `npx prisma migrate deploy`, `npm run build`, `npm start` (Node.js 22 LTS). Configure `DATABASE_URL`, `PORT` (default 3000), `FRONTEND_ORIGINS` (comma-separated exact HTTPS origins), `SESSION_SECRET`, and optional Google variables. Never expose Supabase service credentials to the runtime backend.

Before production, explicitly verify with FPS.ms support/account UI that the deployment contract honors `PORT`, starts the declared command, exposes the selected port, supports HTTP upgrade/WebSockets, supplies environment variables, and provides MariaDB/TLS for the selected paid plan. Those contract and account settings have not been verified here; this document is not a deployment claim.

Apply migrations only after a separately approved backup: `cd backend && npx prisma migrate deploy`. Take and verify a MariaDB backup using the provider's supported snapshot/export mechanism before every schema rollout; rehearse restore into a separate database, verify row counts/checksums without logging save payloads, then switch the `DATABASE_URL`. The app does not perform backup/restore automatically.

CORS is deny-by-default and credentialed only for exact configured origins; set the browser to `credentials: include`. Cookies are HttpOnly, Secure and SameSite=None and therefore require public HTTPS. Use WSS from the frontend. The WebSocket upgrade requires an exact allowed Origin; REST `GET /api/v1/game/state` is the resynchronization source. Current WS implementation only sends a connection acknowledgement; event publication after game-state commits is not yet implemented. `GET /healthz` returns 200 only after DB connection; it reveals no secrets.

The import script is dry-run unless `--apply` is explicit, requires `MIGRATION_BACKUP_APPROVED=YES` to apply, preserves UUID and JSON where its expected `player_saves` shape matches, and never mutates source. Review its schema assumptions and run from repository root after backend dependencies exist. Supabase password hashes and sessions are not imported. Existing identities may require reauthentication/password reset through a real configured provider; no fake email/reset mechanism is provided. Google token verification requires `GOOGLE_CLIENT_ID`; account-linking is not enabled yet.

This is an implementation foundation, not a completed migration. Game command handling, server battle execution/rewards, expedition settlement, economic ledger/idempotency transactions, and post-commit WS events remain disabled and must be completed before production or client cutover.
